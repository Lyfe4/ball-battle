# BallBattle audit, November 2026

An independent review of `main` at `f9f3ac4` (ruleset 14), done before work starts on a backend
(accounts, async PvP, leaderboards, later live PvP and purchases; `docs/vision.md`, "Long-term
goal"). It is an audit only: nothing on `main` was changed.

**How it was done.** I read CLAUDE.md, the README, `docs/vision.md`, the ADR list, `package.json`,
the CI workflow, `netlify.toml`, the configs and the code. I also ran:

- `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm test:slow`, `pnpm build`, `pnpm audit` and
  `pnpm outdated`;
- the failing home-resume flow 8 times locally;
- small scratch scripts against the sim (timing `verifySeries`, fuzzing its input, recomputing
  every ball's shape, and the draw rate of the flaky test's series).

I pulled CI job timings and the failing logs of PRs #38 and #39 with `gh`, and decoded the court
pictures from the failed reload assertion.

Severity labels:

- **Must fix**: must be fixed before the backend.
- **Should fix**: should be fixed, soon.
- **Nice**: nice to have.

Size labels: **XS** under an hour, **S** half a day, **M** one to two days, **L** more than that.

---

## Summary

This is a well-built project. A pure, deterministic simulation is enforced three ways: a separate
tsconfig, ESLint bans and the ruleset fingerprint. Results are checked bit for bit in V8,
SpiderMonkey and JavaScriptCore. The TypeScript settings are about as strict as it gets. The
production code has no `innerHTML`, every storage read is validated and fail-safe, and the CSP is
strict. The bundle is small (about 82 KB gzipped for JS and CSS). **The core is ready to run on a
server as it is**: Node 24 runs `verifySeries`, `playSeries` and the bots straight from
`src/sim`, and verifying a Best of 3 takes about 14 ms.

What needs work before a backend:

1. **`verifySeries` is not yet a safe gate for untrusted input.** It accepts an unknown `format`
   or `opponent.kind` and throws on malformed JSON instead of refusing it. Its only runtime
   decoder lives in the app layer.
2. **The seed design leaks the future.** Whoever holds `SeriesSetup.seed` during the draft can
   simulate every candidate pick. That is fine against a bot in a static site, but fatal for PvP
   and leaderboards. It needs a design (secret per-round seeds, commit-reveal) before any
   competitive mode.
3. **One build verifies only one ruleset.** An async series that spans a deploy can't be
   verified.
4. **The test suite has two real flakes**, both understood below and both cheap to fix. The
   browser jobs take 7.5 to 9.5 minutes each, which is the critical path of every PR.
5. **Process debt in the docs**: 50 ADRs, many superseded; a 347-line CLAUDE.md; a stale README.
   There are also a few files at the 300-line limit and some stale balance notes.

Two things in the brief turned out not to be true, and the report says so where they come up:

- **The shape exceptions are not stale.** Every one of them is still needed today, by the map
  and by the measurement. They can be **tightened**, not removed.
- **The home-resume timeout is not mainly about random seeds.** Seeds do matter, and the test
  should not use them, but the stall itself is something else.

## 1. Architecture and structure

The folder layout follows CLAUDE.md:

- `src/sim` holds the pure sim.
- `src/render` only draws.
- `src/ui` is the plain-DOM HUD.
- `src/app` holds pure browser helpers.
- Each screen has a controller module.

There are 46.5 k lines of TypeScript and CSS: 25 k of source and 14.8 k of tests. I found no dead
production code beyond three helpers. There are no TODOs or `eslint-disable` lines in production.

### 1.1 `main.ts` is at the line limit and depends on declaration order (should fix, M)

ESLint counts lines with `skipBlankLines` and `skipComments` (`eslint.config.js:63`).
`src/main.ts` sits at **300 of 300**, so the next change to it fails lint.

Its controllers capture bindings that are declared further down:

- `held: () => series.held()` at `main.ts:117` uses `series`, which is declared at :211.
- `showWorld` and `started` use `arena`, which is declared at :256.

This works only because no constructor calls its host synchronously. If one ever does, the page
dies at load with a TDZ `ReferenceError`.

`showControls()` (`main.ts:322-347`) is a hand-written visibility table, one `setVisible` per
screen, plus `isSetup()` and `TITLES`. A new screen has to touch three places. That works against
the router's own "a new screen adds one handler, not a branch" (`src/app/router.ts:2`).

```ts
// main.ts:316
function isSetup(): boolean {
  const screen = router.current();
  if (screen === 'series') return !series.isPlaying();
  return screen === 'pick' || screen === 'manual' || screen === 'modes' || screen === 'outdated';
}
```

**Fix:**

- Each route handler declares its own `{ visible, isSetup, title }`.
- `showControls` becomes a loop in a small `layout.ts`.
- Build the arena before the controllers (or hand them a lazy host).

### 1.2 Screen modules sit at the `src/` root with two suffixes (nice, S)

These files sit next to `arena.ts` and `main.ts`:

- `home-controller.ts`
- `quick-controller.ts`
- `series-setup.ts`
- `series-controller.ts`
- `series-screens.ts`
- `manual-screen.ts`
- `modes-screen.ts`
- `outdated-screen.ts`

`-controller` and `-screen` mean the same thing. A newcomer only finds that out from CLAUDE.md
rule 5.

**Fix:** move them to `src/screens/` with one suffix. It is a mechanical move.

### 1.3 Files close to the limit (should fix, S each)

| File                      | Counted lines       | Note                                                                                       |
| ------------------------- | ------------------- | ------------------------------------------------------------------------------------------ |

### 1.4 Small duplication and stale text (nice, XS)

- `const storage = () => window.localStorage` is defined three times: `main.ts:58`,
  `modes-screen.ts:27` and `series-setup.ts:43`.
- `TITLES.series` is `'Best of 3 · BallBattle'`, then patched for Best of 5 by re-parsing the URL
  (`main.ts:345`).
- `index.html` still says `aria-label="Best of 3 setup"`, and its meta description says "three

Adding a ball takes about nine files: the definition, the `BALLS` order, a counter-map file, the

golden and the balance summary. Almost all of these steps are enforced by tests. One small
inconsistency: the main colour lives in the definition and the accent in `theme.ts`.

## 2. Backend readiness

### What already works

- **`src/sim` is server-safe today.** Outside its own folder it imports only `vitest` and
  `node:crypto`, both in tests. It has no `import.meta`, no `?raw` and no CSS.
  `tsconfig.sim.json` has `"lib": ["ES2023"], "types": []`, so a DOM global is a type error.
  Node 24 runs `verifySeries`, `playSeries` and the bots straight from the `.ts` source.
- **Cost of verifying on a server** (measured, 30 Hard-bot Reveal series each):

  | Series    | Time   | Matches | Ticks per match |
  | --------- | ------ | ------- | --------------- |
  | Best of 3 | ~14 ms | ~2.5    | ~1,070          |
  | Best of 5 | ~32 ms | ~4.4    |                 |

  Ticks cost about 5–7 µs each. The hard cap is `MATCH_TIME_LIMIT_TICKS = 3600`
  (`constants.ts:17`), so the worst case is Best of 5 × 3 attempts × 3600 = 54 k ticks, about
  0.3–0.5 s of CPU. That is fine, but run it in a worker pool, not on the request thread.

- **Determinism risk is low:**
  - The ESLint ban covers every transcendental `Math` function and `**`.
  - Sim code never iterates object keys.
  - Both `.sort()` calls sort id strings.
  - Ability-state keys are `ball-N`, not integer-like, so their order survives JSON.
  - Golden results already prove V8, SpiderMonkey and JavaScriptCore agree, and Node is V8.
- **Text in definitions is not a server cost.** The ball files and the counter map are about
  290 KB of source, mostly comments. Don't split it out.

### 2.1 `verifySeries` is not a total function over untrusted input (must fix, S–M)

Probed with scratch scripts:

- A valid Showdown series with **`format: 'weird'`** returns `ok: true`. `formatOf` passes the
  string through, and `awaitingPick` treats anything that isn't blind or reveal as Showdown
  (`series.ts:216`).
- **`opponent: { kind: 'banana' }`** returns `ok: true`. The bot checks only run when
  `kind === 'bot'`, so an unknown kind behaves like `'player'` and skips them:

  ```ts
  // src/sim/series-verify.ts:65
  const { opponent } = setup;
  const bot = opponent.kind === 'bot' ? BOTS.get(opponent.bot) : undefined;
  if (opponent.kind === 'bot') {
    /* lineup and pick checks */
  }
  ```

- **`a: 'abc'`** throws `TypeError: ids.every is not a function`, and **`opponent: null`**
  throws reading `kind`. It throws instead of returning a verdict.
- **`ruleset: "14"`** (a string) is refused with "Played under ruleset 14, not 14".

Today the type system keeps all of this out. A server receives `unknown` JSON.

**Fix:**

- Add one total decoder to the sim:
  `parseSeriesSetup(raw: unknown): { ok: true; setup } | { ok: false; reason }`.
- Have `verifySeries` refuse an unknown `format` or `opponent.kind`.
- Keep it the single gate, as CLAUDE.md asks.
- **Test:** fuzz with arbitrary JSON and assert it never throws, plus explicit cases for `'weird'`
  and `'banana'`.

### 2.2 The only runtime decoder lives in the app layer (should fix, S; do it with 2.1)

`asSetup` in `src/app/series-save.ts:131-164` is the only runtime validator of a `SeriesSetup`.
It accepts only `kind: 'bot'`, and its module imports `../ui/lineup-draft.ts`, so a server can't
take it.

**Fix:** move the decoder into `src/sim` (2.1) and have `series-save` call it.
`src/app/series-url.ts` is the client's link format, not a wire format, and can stay in app.

### 2.3 The seed decides the draft's future (must fix before any competitive mode, design)

`SeriesSetup.seed` decides every round seed, the Reveal coin toss and the bot's lineup.

- The client holds it during the draft (`generateSeed()` in `src/series-setup.ts:138`). It can
  simulate each candidate pick (14 ms a series) and play the winner. That turns the draft, which
  `docs/vision.md` says is where the skill is, into a lookup.
- Hiding the series seed and revealing only round seeds doesn't help either. `deriveSeed`
  (`rng.ts:50-58`) is a reversible murmur3 finaliser over 32 bits.
- The vision's rule "the server issues seeds" is necessary but not sufficient.

This doesn't matter for today's single-player game. It does matter for async PvP and for any
leaderboard, bot ladders included.

**Fix (design, write an ADR first):**

- Each round's seed is secret until both picks for that round are locked. For example, derive it
  as `HMAC(serverSecret, seriesId, round)` and reveal it after the picks.
- Showdown's simultaneous picks need commit-reveal.
- `verifySeries` then takes the revealed round seeds, or the server alone verifies.

### 2.4 One build verifies only one ruleset (should fix before async PvP, design)

`if (setup.ruleset !== RULESET_VERSION) return fail(...)` (`series-verify.ts:56`). An async series
that spans a deploy can never be verified.

**Fix:** pin the ruleset when a series is created. Either keep old sim builds side by side
(`packages/sim@14`, `@15` as versioned bundles, loaded by `ruleset`), or drain open series before
a bump. Decide this in an ADR alongside 2.3.

### 2.5 Packaging: no public entry point (should fix when the backend starts, M)

92 non-test files outside the sim import 36 different sim modules directly.

**Before a server exists:**

- Add `src/sim/index.ts` with the server API:
  - `createWorld`, `step`, `BALL_LOOKUP`
  - the series functions, `verifySeries`, the new decoder
  - `BOTS`, `RULESET_VERSION`
- Then move `src/sim` to `packages/sim` in a pnpm workspace with an `exports` map.
- Add `erasableSyntaxOnly` to `tsconfig.sim.json`, so Node's type stripping keeps working. Or use
  `rewriteRelativeImportExtensions` if you compile.
- Export a bound `verifySeries(setup)` that always uses `BALL_LOOKUP`. The bot picks by index
  into the lookup's order, so a server must not be able to pass another lookup by mistake.
- Normalise optional defaults before hashing or storing a setup: `bestOf: 3` and an absent
  `bestOf` are the same series.

### 2.6 The ESLint purity guard has a hole (should fix, XS)

`no-restricted-imports` for the sim bans only `**/render` and `**/main`
(`eslint.config.js:119`). An import from `src/app` or `src/ui` isn't flagged, and
`tsconfig.sim` only catches it if the imported file happens to use DOM types.

**Fix:** ban every path that leaves `src/sim` (`**/app/**`, `**/ui/**`, `**/styleguide/**`,
`**/flows/**` and so on). This matters even more once the sim is a package.

### 2.7 Client-only assumptions to plan around (should fix, with the backend)

- **Two tabs share one saved series.** Both write `ballbattle.series` (`series-save.ts:25`) and
  nothing listens for `storage`. Scenario: a series runs in tab A, a new series starts in tab B,
  then tab A is reloaded. Tab A now restores B's series, or B's "Leave" clears A's.
  - **Fix:** a per-tab id in `sessionStorage` stored with the save, or a `storage` listener that
    drops this tab's claim.
  - **Test:** two frames sharing storage.
- **Accounts.** On a shared device, a held series resumes for the next person. Clear the
  `ballbattle.*` keys on logout. The server owns the series once it exists.
- **The bot's "hidden" lineup is UI-only.** Anyone can compute `pickLineup(seed)` from the URL.
  That's fine against a bot, but PvP must never send an opponent's lineup early (2.3).

## 3. Code quality

### Good, keep

- **TypeScript is maximally strict:** `strict`, `noUncheckedIndexedAccess`,
  `exactOptionalPropertyTypes`, `noPropertyAccessFromIndexSignature`, `noImplicitOverride` and
  ESLint `strictTypeChecked`.
- **The sim has almost no escape hatches.** It has no `any` and no non-null `!`. There is one
  documented `as unknown as` in `define-ball.ts:13`, and four ability-state casts.
- **Errors are handled at the right level:**
  - Internal invariants throw (`recordPick`, `getDefinition`).
  - A sim exception during a frame stops only that match and shows a `role="alert"` message
    (`arena.ts:98-110`).
  - A clipboard failure falls back to text.
- **Comments are consistent and explain why**, not what.

### Weak spots

- **Hardest to change:**
  - `main.ts` (1.1).
  - The `series-controller.ts` and `series-setup.ts` pair, with many host callbacks between them.
  - `bot.ts`, `bot-model.ts` and `maximin.ts`: reordering any arithmetic changes bot choices and
    needs a ruleset bump. That is guarded, but fragile.
- **Startup failure is blank (nice, S).** If `getContext('2d')` returns null, or any `getElement`
  fails, it throws during `main.ts`'s top-level code. The whole app stays blank, including the
  screens without an arena, and there is no fallback content in `index.html`.
  - **Fix:** catch at boot and show a static message.

### 4.1 The two flaky browser tests: causes

**(a) `home-resume.*`: "Timed out waiting for round 1 to be decided"**

- **Failures seen:** Firefox and WebKit on PRs #38 and #39 (wide), and WebKit (touch) on run 43290523004.
- **Passing runs** take the whole test in **7–17 s** (CI logs), and so did all 8 local repeats
  (7–26 s). A failure is a full 120 s with nothing happening: **a stall, not a slow round**.

There are two separate defects in the flow, `src/flows/home-resume-flow.ts:59-68`:

```ts
// Round 1, played out: a draw is replayed, so wait until a side has won it.
await waitFor(
  () => {
    shown(framed, '.ready-fight')[0]?.click();
    const [you, bot] = scoreIn(seriesScore(framed));
    return you + bot === 1;
  },
  120_000,
  'round 1 to be decided',
);
```

1. **A drawn round can never finish (confirmed bug, rare).**
   - After a draw the series screen is `between`, with the action `play`: a **"↻ Replay round"**
     button (`seriesScreenOf`, `src/ui/series/series-view.ts:230`; `series-panel.ts:252-256`).
   - No ready card is shown until that button is pressed. The loop only ever clicks
     `.ready-fight`, so after a draw it waits forever. The comment's assumption is wrong.
   - How often: I replayed this test's exact series (lineup Storm, Berserker, Brawler, Reveal,
     first pick row) for seeds 0–399. Round 1 draws on 0 of 400 seeds at Easy, 1 of 400 at Normal
     and 2 of 400 at Hard.
   - So it is real but rare. It explains maybe one failure in two hundred, not the rate seen.
2. **The series is random, so a failure can't be replayed.**
   - Home's Play calls `generateSeed()` (`crypto.getRandomValues`, `src/app/seed.ts`), so every
     run fights a different bot lineup, toss and round.
   - The bot level is whatever an earlier file in the same project left in `localStorage`
     (`browser-setup.ts` clears only the series keys).
   - The failure's seed isn't logged, so no failure can be reproduced.

**The stall itself.** None of the code paths I traced (ready card, `isPaused`, the series
controller's `settle` and `update`) can stall with a decisive round and a running frame loop.
Every one of them needs `requestAnimationFrame` to keep firing.

The pattern fits frames being starved or paused in the test page under CI load:

- It happens only under CI load, never locally in isolation.
- It happens only in Firefox and WebKit, which throttle or suspend `rAF` in hidden or occluded
  documents more aggressively than Chromium. `arena.ts:242` already handles `visibilitychange`.
- Each engine job runs six browser projects in parallel, each with parallel files, on a 4-vCPU
  runner.

I could not prove this without CI access. The next step makes the next failure say which it is.

**Fix (S):**

- **Pin the seed.** Override `framed.win().crypto.getRandomValues` in the frame before pressing
  Play, so the series is fixed. Pick one whose round 1 is decisive and short.
- **Pin the bot level** in `localStorage`, as `series-reload-flow` does.
- **Handle the replay.** In the wait loop, also click "↻ Replay round" when it shows. Do the same
  in `best-of-5-flow.ts`, which waits only on `.ready-fight` between rounds.
- **Make the timeout explain itself.** Include in the message:
  - the series phase;
  - the arena's world tick;
  - `document.visibilityState` of the frame;
  - frames drawn in the last second;
  - the seed.

  If the tick isn't moving and frames are about 0, it is rAF starvation, and the fix is fewer
  parallel files per engine (`maxWorkers`) or sharding (4.3).

- **Wait on progress, not wall time.** Fail fast if the world tick stops advancing for 10 s, instead
  of waiting 120 s.

**(b) `series-reload.*`: court picture differs after a reload**

The failure on PR #38 (Chromium, wide, round 2's Fight! moment, Titan vs Thorns): I decoded both
PNGs from the CI log.

- They differ in **exactly 3 pixels of 589,824, each by one colour step** (for example
  `(17,127,58)` vs `(17,127,57)`).
- All three are on the **anti-aliased left and right edges of the still Thorns ball**.

That is not a different scene. It is the same shapes rasterised slightly differently.

`settleHold` (`src/app/playback.ts:66`) already makes the held effect time exact by
construction, and `introLook` returns exactly `{ scale: 1, alpha: 1 }` at that moment
(`render/motion.ts:69-71`). So the earlier clock-drift explanation no longer applies.

The likely cause is how the canvas is rasterised before and after the reload:

- **Before the reload,** `steady()` has read the canvas with `toDataURL()` every 400 ms for the
  whole series. Browsers move a canvas that is read back often from GPU to CPU rasterisation, and
  Chrome does this explicitly.
- **After the reload,** the fresh canvas draws the held moment **once**. The held loop returns
  early and never redraws (`arena.ts:186-189`), so that one picture stays on whichever path the
  new canvas started on.
- GPU and CPU anti-aliasing of the same arc differ by one step on a few edge pixels.

**Fix (S), either:**

- **Compare with a tolerance:** at most a handful of pixels, each at most 2 steps apart. That is
  enough to catch any real difference (a wrong ball, a missing effect, a moved ball), which
  changes thousands of pixels.
- **Compare what was asked to be drawn**, not pixels: the world hash, the effect time and the
  active effects at the held moment.

Creating the arena context with `{ willReadFrequently: true }` in tests only would also confirm
the diagnosis, since it pins the CPU path from the start. Don't ship that to players.

### 4.2 Heavy tests run in the unit suite on the default 5 s timeout (should fix, S)

On a loaded machine (about 80% CPU from other work), `pnpm test` failed with 4 and then 7 tests
over Vitest's 5 s default. They pass in CI and when run alone. They play whole series or every
pair:

- `src/sim/ruleset.test.ts` (8.8–10.9 s)
- `series-verify.test.ts` "accepts every series" (6.5–9.6 s)
- `series-verify-best-of-5` (7.9 s)
- `scripts/reveal-analysis.test.ts` (7–9 s)
- `scripts/best-of-n-bot.test.ts` (5.6–7.6 s)
- `series-save-best-of-5.test.ts` (5–6 s)
- `scripts/balance-jobs.test.ts` (5.2 s)

The pre-commit hook and contributors will hit this.

**Fix:** move the roster-wide ones into `slow`, or give each an explicit timeout. The unit suite
should stay well under a second per test.

### 4.3 The slow suite: one serial 2-minute test against a 120 s ceiling (should fix, S)

`src/sim/balls/pass-through.slow.test.ts` is one `it` over 276 pairs × 60 seeds. Locally it timed
out once at 130 s against `ROSTER_TIMEOUT_MS = 120_000`. It grows as N².

**Fix:** split it with `it.each` per ball, or into chunks of pairs, so Vitest runs it in parallel
and each piece has its own budget. Do the same for `determinism.slow`.

### 4.4 Cutting CI time (should fix, M)

The browser jobs are slow because flows play real matches in real time. Speed is set to 2, there
are waits of up to 150 s per round, and `series-reload` plays three whole series per size per
engine, at three sizes.

In order of value:

1. **Play whole series at one size per engine.** At the other sizes, assert the screens at the
   ready, mid-fight and result moments without fighting out every round. This alone roughly
   halves the jobs.
2. **Add a test-only presentation time scale.** Expose a high multiplier through the presentation
   clock, set by `browser-setup.ts` and kept out of production builds. ADR 0007 already
   guarantees that sim results don't change with presentation time.
3. **Shard each engine 2 ways** (`vitest --shard=1/2`). That gives 6 browser jobs of about 4 min
   instead of 3 of about 9.
4. **Drop the full re-run on `push: main` after merging an up-to-date branch,** or run only the
   check job there. Today every merge spends another 9+ minutes.

Expected result: a PR's wall clock goes from 19–22 min to about 8–10.

## 7. Security

### Today: sound, keep it as it is

- **CSP** (`netlify.toml:17`): `default-src 'none'; script-src 'self'; style-src 'self'; …
base-uri 'none'; form-action 'none'; frame-ancestors 'none'`.
- **Other headers:** COOP, CORP, nosniff, `Referrer-Policy: no-referrer` and a Permissions-Policy.
- **Preview matches production.** `scripts/security-headers.ts` serves the same set to
  `vite preview`, and a test keeps it in step with `netlify.toml`.
- **No DOM injection sinks in production.** The only `innerHTML` is in a test helper
  (`src/flows/look-checks.ts:47`). All text goes through `textContent` (`src/ui/dom.ts`).
- **Every `localStorage` access is fail-safe.** Each one is in try/catch behind a getter, so
  private mode and a full quota can't throw. Saved data is validated field by field:
  - integers are capped at uint32;
  - ids are allow-listed against the roster;
  - the draft length is capped;
  - the format and bot are allow-listed;
  - the whole series is then re-verified by `verifySeries`, and a bad save is deleted
    (`series-save.ts:119-182`, `series-restore.ts:84-89`).
- **Hostile input can't hang the page.** A `plays: 4e9` stops when the series ends.
- **URL parsing is strict.** `parseSeed` accepts only `/^\d{1,10}$/` up to uint32, so NaN, hex,
  negatives and exponents all fall back (`seed.ts:8-12`). Ball ids are allow-listed, and picks are
  length-capped before they are checked.
- **No open redirect.** Navigation only rewrites search params.
- **Nits:**
  - `parseSeriesLength` uses `Number()`, so `"0x5"` reads as 5 (`series-length.ts:11`).
  - Lineup strings are split before any length cap (`series-url.ts:83`). The URL length limit
    bounds them.

### Before real accounts and payments (must fix, S each)

1. **Add `connect-src`** for the API origin. Today `default-src 'none'` blocks every `fetch`.
2. **Auth tokens go in `HttpOnly; Secure; SameSite` cookies, never `localStorage`.** Anything in
   `localStorage` is readable by every script on the origin. Add CSRF protection to match: a
   SameSite=Lax/Strict cookie plus an `Origin` check, or a token.
3. **Add an explicit `Strict-Transport-Security`** header rather than relying on Netlify's
   default.
4. **Add `require-trusted-types-for 'script'`.** It costs nothing, since production has no HTML
   sinks, and it locks that in.
5. **Payments:** load a provider's script or iframe only on the payment route. Scope `frame-src`
   and `script-src` to it there, and relax `payment=()` only there. Never handle card data
   yourself: use the provider's hosted fields or checkout.
6. **Logout clears `ballbattle.*`** (2.7).
7. **The server never trusts the client.** It issues seeds (2.3), verifies every result with the
   sim decoder plus `verifySeries` (2.1), runs verification in a worker with a CPU budget, and
   rate-limits submissions per account. Don't rate-limit per IP alone: families, schools and
   mobile carriers share IPs.

## 8. Performance

- **Load:** about 82 KB of gzipped JS and CSS, one self-hosted subset font with `swap`, and
  `immutable` caching on `/assets/*`. Good.
- **Frame time on a phone:**
  - Each frame is a full vector redraw of a two-ball scene, with no `shadowBlur`, gradients,
    filters or `drawImage` in `src/render`.
  - The device pixel ratio is capped (`theme.maxPixelRatio`, `canvas.ts:25`).
  - Frames where nothing changes skip drawing (`arena.ts:224-235`).
  - That is cheap on any phone. Offscreen caching of ball designs isn't needed.
  - `scripts/frame-timing.ts` exists to measure it.
- **Memory:** effect arrays are pruned and reset on every `show` (`arena.ts:264-266`). Screens
  build their DOM once. Settings and leave-confirm add and remove their listeners in pairs. There
  is no growth over a long session.
- **Small items (nice, XS–S):**
  - The rAF loop keeps scheduling behind setup screens. Paused frames return early, but on a
    phone it is still a wake-up per frame. Stop scheduling while paused.
  - An open symbol legend keeps its document `keydown` listener after its screen is hidden
    (`symbol-legend.ts:64-68`). Close legends in the router's `leave`.
  - A finished series link plays the whole series twice: once in `parseRoute`'s `verifySeries`
    (`route.ts:153`) and once in the controller. That is about 14–32 ms. Measure before acting.

## What's genuinely good, and should survive any cleanup

- **The pure-sim contract and its three guards:**
  - `tsconfig.sim.json` with no DOM lib;
  - the ESLint bans on globals, transcendental `Math` and `**`;
  - the append-only ruleset fingerprint.

  This is what makes a backend cheap.

- **Golden results in Node, V8, SpiderMonkey and JavaScriptCore,** with `pnpm golden` refusing
  to rewrite without a version bump.
- **`verifySeries` as the one gate** used by links, saves, `playSeries` and (later) the server.
  Every match has a hard tick cap, so verification always ends.
- **Hooks return actions; `step` is pure.** Ability state is typed per ball. The seeded PRNG
  state lives in `WorldState`, and each hook call gets its own derived stream.
- **Presentation time is separate from sim time** (ADR 0007), so feel work can never change a
  result.
- **Maximal TypeScript strictness,** almost no casts, and comments that explain why.
- **Security posture:** a strict CSP mirrored in preview by a test, no HTML sinks, validated and
  fail-safe storage, strict URL parsing.
- **A lean bundle** with one runtime dependency, and a renderer that is cheap on phones.
- **Real accessibility work:** focus management, live regions, reduced motion in CSS and canvas,
  and contrast tests.
- **A balance pipeline with fixed seeds** and noise-aware bands, plus a generated summary.
- **Careful CI:** SHA-pinned actions, keyed browser caches, a per-engine matrix, cancellation of
  superseded runs.
- **Honest ADRs and experiment write-ups.** Keep them; index them.
